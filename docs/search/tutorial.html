Part 1

Text search — fast and forgiving

No AI. The goal: find Renew passport when you type pasport, pass or renewing, in about a millisecond.

Step 1 · Pick or type a task title

Text → terms (tokenizing)

Before anything can be searched, every task title is broken into terms — the small, standardised pieces the search actually compares. Your search box text goes through exactly the same steps, so two different spellings of a word end up as the same term and match.

Colours: blue = an ordinary term (a word, or one Chinese character). purple = a bonus term for two neighbouring Chinese characters — Chinese has no spaces, so the search can't tell where words end; storing pairs lets 牙医 score higher on a task containing exactly 牙医 than on one where 牙 and 医 are far apart.

Step 2 · Look up a word

The inverted index — like the index at the back of a book

Reading every task on every keystroke would be slow. Instead, the terms from step 1 are collected once into a lookup table: term → which tasks contain it, and where. A search then just looks its terms up — like finding “passport” in a book's index instead of reading the whole book.

Step 3 · Edit the words

Typos: edit distance

Why we need it. Step 2 only finds terms that are spelled exactly right. Type pasport and step 1 turns it into the term pasport — which no task contains, so the lookup finds nothing. To forgive typos, the search compares your term with the terms in the index and keeps those that are only one or two letters off. “How many letters off” is the edit distance: the fewest single-letter changes — insert one, delete one, replace one, or swap two neighbours — that turn one word into the other.

How the table works. Rows are the letters of the first word, columns the letters of the second. The cell in row i, column j answers a smaller question: how many edits turn the first i letters of the first word into the first j letters of the second? The top row and left column are easy (from nothing to 3 letters = 3 inserts). Every other cell is the cheapest of three moves from a cell already worked out:

  • Move diagonally, from the cell one up and one left to this cell: both words gain one letter. Free (+0) if the two new letters are the same; +1 if they differ (replace one with the other).
  • Move down, from the cell directly above to this cell: only the first word gains a letter, so that letter has to be deleted, +1.
  • Move right, from the cell directly to the left to this cell: only the second word gains a letter, so it has to be inserted, +1.

Why the diagonal is its own move. In the table it lands where “down, then right” would — but it's cheaper. For pa → pt, down-then-right means delete “a”, then insert “t”: 2 edits. The diagonal replaces “a” with “t”: 1 edit. And when the letters match (pa → pa) it's free, where down-then-right would delete “a” and insert it again for 2. A mistyped letter is one typo, so it should cost one edit, not two. (The swap move exists for the same reason: two swapped letters would otherwise cost two replaces.)

As a formula, with A the first word, B the second and D[i][j] the cell in row i, column j:

D[0][j] = j          D[i][0] = i
D[i][j] = min( D[i-1][j-1] + (A[i] == B[j] ? 0 : 1),   // diagonal: keep or replace
               D[i-1][j]   + 1,                        // down: delete A[i]
               D[i][j-1]   + 1,                        // right: insert B[j]
               D[i-2][j-2] + 1  if A[i-1..i] is B[j-1..j] swapped )   // swap neighbours

Filling cells left-to-right, top-to-bottom means each answer reuses three earlier ones (this trick is called dynamic programming). The bottom-right cell covers all letters of both words, so it is the answer — the other cells are stepping stones. The blue path traces back which moves produced that answer, so you can read the actual edits off it (listed above the table). Hover any cell to see what it means.

Where it goes next. Short words would match everything with typos allowed, so: words of 4–6 letters may be 1 edit off, 7+ letters 2, shorter words must be exact. A typo match counts for less than an exact one — in step 4 you'll see it as typo ×0.6.

Step 4 · Search the sample planner

Scoring: what each match is worth

Each query word expands to index terms it could mean — exact ×1 word start ×0.75 typo ×0.6. A match earns factor × IDF × field weight (field weight from step 2: title 3, project/repeat 1.5, notes 1). Results matching more of the query come first. Phrases like “last month”, “done” or “bills” become filters.

IDF — “how rare is this word?” Short for inverse document frequency. A word that appears in almost every task (like “call” or “pay”) tells you little about which task you mean; a word in only one task (like “passport”) points straight at it. So each term gets a rarity score:
IDF = ln(1 + N / n)  N = number of tasks, n = tasks containing the term
The rarer the word, the bigger its share of the score. (The “1 +” keeps it above zero even for a word in every task.)

Part 2

Search by meaning — embeddings

Text search can’t connect teeth with Call the dentist — no letters in common. An embedding model turns each text into a vector (bge-m3: 1,024 numbers) so that similar meanings point in similar directions.

Step 1 · Drag the arrows

Similarity = the angle between arrows

Real vectors have 1,024 dimensions; here are 2 so you can see them. Cosine similarity is the cosine of the angle: 1 = same direction, 0 = unrelated. Drag the dots at the arrow tips; the shaded wedge is the angle between the query and the arrow you last touched.

If every arrow is stored at length 1 (“normalized”), cosine similarity is just the dot product: a₁b₁ + a₂b₂ (+ … 1,024 terms).
Why no vector database? To search, we compare the query with every task — “brute force”. Each comparison is 1,024 multiply-adds, so:
tasksmultiply-addstime (roughly)memory
3,000 (a busy planner)3 million~3 ms12 MB
100,000100 million~160 ms400 MB
10 million10 billion~16 s40 GB
A planner stays in the first row for years, so a plain loop in the browser is instant, exact (it never misses the best match), and needs nothing to install or keep in sync.

A vector database (e.g. pgvector, Qdrant, Pinecone) earns its keep around the last row: millions of documents, many users searching at once, or data that doesn't fit in one computer's memory. It builds an approximate nearest-neighbour index (HNSW, IVF…) that only looks at a small, promising part of the vectors — milliseconds instead of seconds, at the cost of occasionally missing a match, extra memory, and a server to run.

Times measured with a plain JavaScript loop on a MacBook (10 million extrapolated); memory is 1,024 numbers × 4 bytes per task.

What you embed matters

The first version also embedded the date and status. It made matches worse — the vector partly “means” a date now. Dates became exact filters instead.

Step 4 · Edit a task

Keeping the index current — fingerprints

Embedding everything takes seconds, so it’s done once and kept. Each stored vector remembers a fingerprint (a hash) of the text it came from. After any change, only items whose fingerprint differs get re-embedded. Rename a task: one re-embed. Move it to another day or tick it done: nothing, because dates and status aren’t part of the text.

Step 5 · Move the slider

Merging two result lists — Reciprocal Rank Fusion

Text scores and cosine similarities are on unrelated scales, so they can’t be added. RRF only uses positions: each list gives an item 1 / (K + rank), and the votes add up. Items in both lists rise to the top.
